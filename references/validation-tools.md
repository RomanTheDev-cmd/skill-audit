# Артефакты, новые сценарии и прерывание

Эти инструменты запускаются при разработке/проверке навыка по запросу, а не перед каждой обычной задачей.

## Привязка первичного подтверждения

`verify_evidence.py` читает только явно названные файлы. `--root` — база относительных путей, не команда обхода всего каталога. Путь за пределы root, в том числе через ссылку, не читается. Результат хранить вне проверяемого навыка, в проекте. Скрипт не запускает заявленную команду.

```json
{
  "criterion": "export_units",
  "claimed_status": "PASS",
  "required_bindings": ["input", "checker", "report"],
  "bindings": {
    "input": {"path": "part.stl", "sha256": "64 реальных hex-символа"},
    "checker": {"path": "check.py", "sha256": "64 реальных hex-символа"},
    "report": {"path": "report.json", "sha256": "64 реальных hex-символа"}
  },
  "basis": {"kind": "execution", "command": "фактическая команда", "exit_code": 0},
  "primary": {
    "binding": "report",
    "status_pointer": "/status",
    "binding_pointers": {"input": "/input_sha256", "checker": "/checker_sha256"}
  }
}
```

Поля первичного JSON выбираются указателями JSON Pointer. Если исходный формат не хранит нужной привязки, не дописывать её в старое подтверждение ради успеха. Указать пробел UNKNOWN; при необходимости сохранить отдельный результат текущей проверки привязки. Полноту `required_bindings`, пригодность метода и соответствие критерия реальной задаче оценивает аудитор. Включать профиль, версии и косвенные зависимости, когда они значимы.

```sh
python3 <источник>/scripts/verify_evidence.py --root <база> --manifest <привязки.json> --out <проект/результат.json>
```

BOUND — объявленные хеши и выбранные поля согласованы; это не PASS предмета и не доказательство запуска. Известное изменение/утрата связанного файла — STALE. Отсутствующая привязка, недоступность, неполный JSON — UNKNOWN. Расхождение заявленного и первичного статуса/хеша либо PASS при ненулевом записанном exit code — INCONSISTENT (подробности сохраняются отдельно). Ошибки привязки могут сосуществовать: проверить все `issues` и `inconsistencies`, не только общий статус. CLI возвращает 0 только для BOUND.

## Пакет без ответов и фиксация решений

13 учебных примеров остаются в `examples/`. Дополнительные шесть — `examples/transfer/cases.json`; происхождение — `provenance.json`, эталон — отдельный `expected.json`. Два случая основаны на воспроизведённых сбоях SC-01/SC-02, остальные — контроли и перенос на другие условия. Это не шесть независимых запусков модели.

```sh
python3 <источник>/scripts/scenario_suite.py prepare --cases <входы.json> --out <пакет.json>
# Исполнителю дать пакет и действующие инструкции; эталон не давать.
python3 <источник>/scripts/scenario_suite.py submit --packet <пакет.json> --actual <решения.json> --out <зафиксированные-решения.json>
python3 <источник>/scripts/scenario_suite.py score --packet <пакет.json> --submission <зафиксированные-решения.json> --oracle <эталон.json> --out <оценка.json>
```

`prepare` не читает эталон. `submit` сохраняет решения вместе с хешем пакета до сравнения; `score` отвергает несовпадение пакета/зафиксированных данных и отдельно считает ложные замечания и пропуски. Это защита порядка работы, не криптографическая подпись и не изоляция доступа. Автор, знающий эталон, не становится независимым исполнителем; доступ свежей сессии к эталонам проверять отдельно. Новый агент/чат — лишь при явном разрешении. Ни имя режима, ни мнение второй модели не доказывают правильность: основания решений сверять с первичными материалами и применимыми условиями.

## Прерывание и локальные проверки

JSON-результаты записываются во временный `.incomplete-*` в той же папке и появляются под итоговым именем лишь после полной записи и fsync, через исключительное создание ссылки. Старый итог не перезаписывается, даже при конкурирующей записи. После аварийного завершения временный файл может остаться; не считать его результатом и не подставлять вместо полного JSON. Повторить незавершённую операцию с тем же ещё свободным итоговым именем, сохранив исходные данные. При ошибке неподдерживаемой файловой операции — сохранить ошибку, не переходить к небезопасной перезаписи. Синхронизация/отказ диска отдельно не доказаны локальным тестом.

```sh
python3 <источник>/scripts/test_tools.py --report <проект/базовые-тесты.json>
python3 <источник>/scripts/test_extended.py --report <проект/расширенные-тесты.json>
```

Первый набор — прежние 50 методов. Второй проверяет привязки, порядок фиксации и реально убивает дочерний процесс посреди записи; его старый результат должен сохраниться, а новый итог оставаться отсутствующим до успешного повтора. Это тест инструментов, не прерванная реальная задача пользователя.

## GitHub

Приватный `RomanTheDev-cmd/skill-audit`, рабочий источник — прежний iCloud. `.github/workflows/checks.yml` запускает только детерминированные тесты и проверку синтаксиса Python при push main, pull_request или ручном запуске. Linux проверяется на Python 3.9 и 3.12. Результаты сохраняются как artifacts для данного коммита. Нет расписания, вызовов моделей и автоматического аудита пользовательских навыков. Успешный CI не доказывает смысловую корректность решений.
