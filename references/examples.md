# Проверка примеров

Тринадцать синтетических сценариев проверяют решения аудита, а не физические свойства предметов. `cases.json` содержит источники как `{файл: [строка1, ...]}`; строки нумеруются с 1. Ожидаемые ответы — отдельный oracle `expected.json`. Они не являются фактическим запуском модели. ID каждого сценария должен быть уникальным; повторный ID — ошибка входа оценщика, а не сокращённый набор проверок.

Парный контроль C8/C13: корректное обязательное условие с UNKNOWN/остановкой при недоступном инструменте не требует замечания; явное требование PASS без выполненной проверки — дефект инструкции. В обоих случаях готовность по непроверенному критерию UNKNOWN.

Сначала прочитать входы и записать фактический ответ вне навыка. Если тот же автор уже знает ожидаемые ответы, отметить это в отчёте. Для каждого ID: classification, status, explanation, basis и findings. Классы: confirmed_defect, possible_risk, optional_improvement, no_issue, insufficient_data. Статусы критериев: PASS, FAIL, UNKNOWN, STALE; NO_CHANGE — решение не править правило.

Пример формы замечания (значения заполняются по исходным данным, это не ответ на конкретный сценарий):

```json
{
  "ID": {
    "classification": "confirmed_defect",
    "status": "FAIL",
    "explanation": "Почему наблюдение нарушает конкретное требование",
    "basis": {"kind": "instruction_analysis"},
    "findings": [{
      "sources": [{"file": "rules.md", "line": 1, "quote": "Точный фрагмент строки"}],
      "scenario": "Входы и условия возникновения",
      "consequence": "Практический результат сбоя",
      "minimal_fix": "Наименьшее исправление причины",
      "verification": {
        "negative": "Случай, который должен ловиться",
        "positive": "Рабочий случай, который должен сохраниться",
        "success": "Проверяемый критерий"
      }
    }]
  }
}
```

Для no_issue: `findings: []`, объяснить применимое условие и почему правка не нужна. Для insufficient_data: также пустые findings, `missing: [конкретные данные]` и `next_step`. Заданный чужой лог — материал анализа; его чтение не является вашим новым запуском. В этих синтетических примерах новые execution/visual/physical не выполняются; допустимый basis задаётся oracle. В настоящем аудите такие виды требуют первичного артефакта, а запуск ещё команды/входов/кода выхода.

```sh
python3 <источник>/scripts/score_examples.py --actual <фактические-решения.json> --out <внешний-результат.json>
```

Оценщик сравнивает класс/статус, проверяет обязательные поля цепочки, точность фрагментов/строк по входу и обязательные источники. Отдельно считает ложные замечания и пропущенные подтверждённые дефекты. Формальная точность цитаты не доказывает, что она логически подтверждает вывод: это отдельно проверяет автор по исходным требованиям. Непустой текст также не доказывает смысловую корректность. Пройдённый пример не гарантирует поведение в новой сессии или на других входах.

Для чтения старых результатов 1.0.0 допускается `--legacy-labels`: сравниваются лишь переданные известные ID и метки; вывод явно legacy_labels_only и не доказывает полноту карточек. Не называть такой счёт полноценной проверкой нового формата.

Контроль оценщика: намеренно испортить источник/проверку положительного случая — пример не проходит; добавить замечание к корректному правилу — false_findings; пропустить дефект — missed_confirmed_defects. Эти мутации проверяют автоматический оценщик, не имитируют мнение независимого аудитора.
